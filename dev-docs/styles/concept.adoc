= Styles

:idprefix:
:idseparator:
:scope_at_rule: https://developer.mozilla.org/en-US/docs/Web/CSS/@scope


This document provides an overview of the styles architecture in OneCX. It explains the core concept of style isolation, how styles are organized and applied, and how different applications coexist on the same page without CSS conflicts.

[#style-isolation]
== Style Isolation

OneCX pages typically host multiple applications simultaneously:

* **Shell UI** — always present, provides the portal layout, navigation, and slot infrastructure
* **Microfrontend (MFE)** — the currently active application, loaded into a Shell slot
* **Remote Components (RCs)** — additional components loaded from various applications into Shell or MFE slots

Each application brings its own CSS, including frameworks (PrimeNG, Material), component libraries, and custom styles. Without isolation, rules from one application would leak into another, causing visual corruption.

[#the-problem]
=== The Problem

In a traditional single-page setup, all styles are global. When multiple applications share the same `<head>` and DOM tree:

* CSS class name collisions cause unexpected styling (e.g., two applications defining `.card { }` differently)
* CSS custom properties (variables) from one theme override another's
* UI framework resets (PrimeNG, Normalize) applied by one application affect all content

[#the-solution]
=== The Solution: CSS @scope

Since version 6, OneCX uses the {scope_at_rule}[CSS @scope at-rule] to create isolated style boundaries. Each application's styles are wrapped in `@scope` rules that restrict them to a specific DOM region identified by data attributes.

[cols="1,3"]
|===
|Mechanism |Purpose

|`@scope` at-rule
|Restricts CSS rules to a DOM range defined by `from` and `to` selectors

|`data-style-id` attribute
|Marks the start of a scoped region with a unique application identifier

|`data-style-isolation` attribute
|Marks the boundary end — styles stop at this element

|`data-no-portal-layout-styles` attribute
|Opt-out of legacy portal layout styles (libs v6+ content)
|===

.Resulting in strict style isolation
[source,html]
----
<body>
  <!-- Shell content -->
  <div data-style-id="onecx-shell|onecx-shell-ui" data-style-isolation>
    ...
    <!-- Slot with MFE content -->
    <div data-style-id="onecx-workspace|onecx-workspace-ui" data-style-isolation>
      <!-- MFE styles only apply here -->
      ...
      <!-- Slot with RC content from a different app -->
      <div data-style-id="other-app|other-app-ui" data-style-isolation>
        <!-- RC styles only apply here, MFE styles do not leak in -->
      </div>
    </div>
  </div>
</body>
----

Each application sets up its own styles. Nothing declared by one application leaks into another's region.

[#style-overview]
== Style Types at a Glance

A OneCX page contains several categories of stylesheets, each with a specific scope and responsibility:

[cols="1,1,3"]
|===
|Type |Scope |Description

|Shell Scoped
|Shell content only
|Styles for Shell UI, scoped to `data-style-id="onecx-shell|onecx-shell-ui"`

|Application Scoped
|Specific application region
|Styles from each application's `styles.css`, scoped to that application's `data-style-id`

|PrimeNG Scoped
|Specific application region
|PrimeNG theme styles, scoped per-application with prefixed CSS variables

|Global Scoped
|Entire page
|Reset, normalize, and truly shared styles (minimal usage)

|Legacy
|Entire page (opt-out available)
|Portal layout styles for backward compatibility; v6+ content opts out via `data-no-portal-layout-styles`
|===

[#browser-support]
== Browser Support

The `@scope` at-rule is a relatively new CSS feature. OneCX handles both native and non-native environments:

* **Native support** — Browsers implementing `CSSScopeRule` use `@scope` directly
* **Polyfill** — The Shell UI includes a MutationObserver-based polyfill that simulates `@scope` behavior for older browsers

For browsers without native support, `@scope` rules are wrapped in `@supports (@scope(...))` blocks, which the polyfill detects and processes.

[#application-styles-overview]
== Application Styles

Each MFE and RC is responsible for providing its own styles. The application exposes a `styles.css` file at its remote URL, which is dynamically fetched, scoped, and injected when the application is activated on the page.

The lifecycle of application styles involves:

1. **Fetching** — Loading `styles.css` from the application's remote URL
2. **Scoping** — Wrapping CSS in `@scope` rules and transforming `:root` to `:scope`
3. **Usage tracking** — Registering which MFEs and RCs are using each style sheet
4. **Cleanup** — Removing styles when no longer referenced by any active component

See xref:application-styles.adoc[Application Styles] for the full lifecycle details.
