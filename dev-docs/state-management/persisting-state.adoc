= Persisting state across reloads with lazy feature slices
:idprefix:
:idseparator: -
:libs: ../../libs
:shell: https://github.com/onecx/onecx-shell-ui/blob/main

== Question answered

How does an App restore its ngrx state from `localStorage` across a page reload, and how is that restore made safe when some feature slices are loaded lazily and are not present in the store yet at boot?

== Why it exists

State that is not derived from the Shell or the URL — drafts, cached data, view preferences — is lost on reload unless the App writes it to `localStorage` and reads it back. The tricky part is lazy loading: on boot, only the eagerly-loaded slices are registered in the store, so a persisted snapshot also contains keys for features that have not been loaded yet. Naively merging the whole snapshot would either clobber those not-yet-loaded slices or throw on keys the current reducer does not know about. The accelerator provides a merge-reducer and a key-configuration helper for exactly this.

== How it works

The two helpers live in `@onecx/ngrx-accelerator` under link:{libs}/ngrx-accelerator/src/index.ts[`src/index.ts`] (both are exported).

=== `lazyLoadingMergeReducer`

link:{libs}/ngrx-accelerator/src/lib/utils/local-storage/lazy-loading-merge-reducer.ts[`lazyLoadingMergeReducer(state, rehydratedState, _action)`] is the `stateReconciler` you hand to a store-persistence setup. On each restore it:

. Collects `keysToRehydrate` with `Object.keys(rehydratedState).filter((key) => state[key])` — in practice, only keys that exist in the *persisted* `rehydratedState` **and** currently have a *truthy* value in the live `state` are selected. A lazy feature that has not loaded yet is excluded because it has no live key, and a present-but-falsy live value such as `false`, `0`, `''` or `null` is also excluded.
. Deep-merges only those keys from `rehydratedState` into the live `state` using `deepmerge`, with `arrayMerge` set to *overwrite* (the persisted array wins, not a concatenation).
. Deletes the merged keys from `rehydratedState`; any keys that were not selected stay in the supplied snapshot object.
. Returns the reconciled `state`.

The effect is that persisted data is applied only to slices selected on *that invocation*. A slice that is still loading lazily is left untouched at boot, and its unmerged persisted key remains in the supplied `rehydratedState` object. Restoring it later is not automatic: the App's persistence integration must invoke the reconciler again while that snapshot is still available after the feature loads. The same caveat applies to present-but-falsy live slice values, because the current truthiness check excludes them from `keysToRehydrate`. This is what makes the helper "lazy-loading"-safe, but only as part of an App integration that re-runs reconciliation when needed.

[source,typescript]
----
import { lazyLoadingMergeReducer } from '@onecx/ngrx-accelerator'

// stateReconciler used with the store-persistence setup:
// merge persisted data only into slices that are already in the store
----

=== `createNestedKeyConfiguration`

link:{libs}/ngrx-accelerator/src/lib/utils/local-storage/create-nested-key-configuration.ts[`createNestedKeyConfiguration(nestedKeyConfiguration)`] converts an App's whitelist of keys into the `KeyConfiguration[]` shape a persistence library expects. It accepts a flat array of `string` or nested `NestedKeyConfiguration` objects and returns it typed as `KeyConfiguration[]`. The related types — `Options` (`serialize`, `deserialize`, `reviver`, `replacer`, `encrypt`, `decrypt`, `filter`, `space`), `KeyConfiguration` and `NestedKeyConfiguration` — describe how particular state keys are (de)serialized and filtered before they touch `localStorage`.

== Libs side / Shell side

=== Libs side

`@onecx/ngrx-accelerator` provides `lazyLoadingMergeReducer` and `createNestedKeyConfiguration`. The App wires them into its own ngrx persistence setup and decides which keys to persist.

=== Shell side

The Shell does not participate in this mechanism. Persistence is a per-App concern against `localStorage`, which is shared by all tabs/windows on the origin. Nothing here crosses the libs ↔ Shell boundary, in contrast to the link:shell-context-to-store.adoc[Shell context → store] and link:url-synced-state.adoc[URL-synced state] Units.

== Angular / React

The helpers are plain TypeScript (they take and return state objects and use `deepmerge`) and do not depend on Angular, so the same code can be used by a React App with its own persistence layer. This is a framework-agnostic part of the Area.

== Edge cases & pitfalls

* Only keys whose current live value is truthy are merged. If a lazily-loaded slice is not in the live store yet, or a present slice currently holds `false`, `0`, `''` or `null`, its persisted value is left in `rehydratedState` and will not appear unless the App later invokes the reconciler again while that snapshot is still available.
* Arrays are *replaced*, not merged: `arrayMerge` is overwritten so the persisted array wins. If you want concatenated history, you must reconcile it yourself.
* `_action` is ignored by the helper — it exists only to match the `stateReconciler` signature.
* `createNestedKeyConfiguration` is a type-level cast; it does not validate the shape, so a malformed key list will only surface at persistence time.
* Encryption and serialization are delegated to whatever `Options` you supply — the helper does not add its own security or (de)serialization.

== Debugging

Inspect the `localStorage` key the App writes (its name depends on the persistence setup) and compare it with the live store: after a reload, the merged slices should match the stored snapshot and the still-lazy slices should be absent until they load. General `window`-state inspection lives in the link:../diagnostics/window-state-inventory.adoc[Diagnostics Area] (planned).
