== Question answered

How does an overlay or dialog that renders outside the app's scope still pick up the owning app's style data when OneCX intercepts creation, and how are wrapping and cleanup handled once the node reaches `document.body`?

== Why it exists

The {scope_at_rule} model (link:{u8}[Unit 8]) confines an app's rules to the DOM subtree that carries its `data-style-id`. Overlays and dialogs are frequently created outside that subtree and therefore need attribution and a body-time promotion step so they receive the correct scoped styles.

Creation-time interception stamps the element with the resolved app style data before the node is appended; the Shell's append-to-body flow then promotes intermediate markers into a scoped wrapper or removes them on cleanup. This Unit documents the generic, framework-agnostic flow for helper registration, creation-time attribution, body append wrapping/blacklisting, cleanup behavior, and stale-trigger edge cases. The container-based alternative is link:{u7}[Dynamic content via container].

== How it works

Two responsibilities cooperate:

* Resolve the owning app from the most-recent trigger element and compute the corresponding StyleData.
* Intercept element creation (at the app/library level) and attach intermediate attributes so the Shell's body hooks can promote or clean up the node when it is appended or removed.

=== The trigger element & closest-ancestor walk

The Shell maintains a lightweight trigger-element accessor (document event listeners that record the last hovered/focused element) and a DOM walk that climbs to the nearest element bearing style markers (`data-style-id` or `data-intermediate-style-id`). The walk reads the style-data keys (style id, isolation flags, and optional MFE metadata) and returns a StyleData object or `null` when no scoped ancestor exists.

This read side is framework-agnostic: any library or app that can obtain the current trigger element and perform the ancestor walk can produce the same StyleData for creation-time attribution.

=== Creation-time interception (framework-agnostic)

At creation time, the app or a library helper may intercept how an overlay/portal is constructed and attach intermediate attributes such as `data-intermediate-style-id` and related keys. The important points for a generic helper are:

* It must resolve the StyleData from the trigger element (via the Shell accessor) immediately before the node is inserted.
* It must only stamp the semantic content node(s) that will be observed by the Shell; it should avoid mutating unrelated portal containers.
* It should use the short-lived `data-intermediate-style-*` attributes so the Shell can promote them atomically when the node reaches the document.

Legacy framework-specific creation helpers (PrimeNG/PrimeReact/Angular Material specific wrappers) are deprecated: prefer a single, small creation helper that libraries or app code can call to add intermediate attributes in a consistent way.

=== Shell append-to-body flow and body hooks

When a node is appended to `document.body`, the Shell's body hooks inspect the subtree for intermediate markers and then either:

* Promote intermediate attributes to permanent `data-style-*` markers and, when appropriate, create a scoped wrapper element that carries `data-style-id`/`data-style-isolation` so the appended content participates in that app's scope; or
* Respect a configured blacklist (for nodes that must remain untouched) and leave them unwrapped.

The Shell's responsibilities are intentionally limited: it promotes/remove markers, creates or finds wrapper containers, and observes removals to clean up wrappers and scoped sections so no orphaned style sections remain after overlays are removed.

== Helper registration and lifecycle

A small set of Shell helpers and body hooks form the contract implementers must use:

* initializeOnecxTriggerElementListener (Shell) — attach `mouseover` / `focusin` handlers and expose the current trigger element via a Shell accessor. link:{shell}/src/app/shell/utils/styles/dynamic-content-initializer.utils.ts[`dynamic-content-initializer.utils.ts`]
* getOnecxTriggerElement (Shell accessor) — returns the current trigger element or a fallback search for a `.onecx-body` descendant with a `data-style-id`. link:{shell}/src/app/shell/utils/styles/onecx-trigger-element.utils.ts[`onecx-trigger-element.utils.ts`]
* appendIntermediateStyleData / appendStyleData (Shell) — utilities to map a StyleData object onto an element's `data-intermediate-style-*` or `data-style-*` attributes. link:{shell}/src/app/shell/utils/styles/style-data.utils.ts[`style-data.utils.ts`]
* createWrapper / findStyleDataWrapper / wrapWithDiv (Shell) — create or locate the wrapper the Shell uses to group appended nodes under a `data-style-id` boundary. link:{shell}/src/app/shell/utils/styles/style-data.utils.ts[`style-data.utils.ts`], link:{shell}/src/app/shell/utils/styles/body-overwrites.utils.ts[`body-overwrites.utils.ts`]
* ensureBodyChangesIncludeStyleData (Shell body hook) — the wrapper/appendChild/removeChild interception that promotes intermediate attributes on append and removes wrappers on removal. link:{shell}/src/app/shell/utils/styles/body-overwrites.utils.ts[`body-overwrites.utils.ts`]
* observeStyleDataWrapper / removeStyleDataRecursive (Shell) — utilities to observe wrapper lifecycle and clean up stale style sections. link:{shell}/src/app/shell/utils/styles/body-overwrites.utils.ts[`body-overwrites.utils.ts`]

Note: small framework-specific helpers (for example, previous PrimeNG/Material-specific creation shims) remain in the codebase for compatibility but are considered deprecated in favor of the single creation-interception helper described above. link:{shell}/src/app/shell/utils/styles/primeng-overwrites.utils.ts[`primeng-overwrites.utils.ts`], link:{shell}/src/app/shell/utils/styles/angular-material-overwrites.utils.ts[`angular-material-overwrites.utils.ts`]
== Edge cases & pitfalls

* Stale trigger element — the trigger accessor holds the last gesture. Programmatic overlays may be attributed to the wrong app or to none; the Shell fallback narrows this but cannot infer intent for code-driven insertions.
* Trigger outside any scope — when no scoped ancestor exists the walk yields `null` and the overlay remains unattributed.
* Helper granularity — creation helpers should stamp the semantic content node(s) only; mutating unrelated portal containers or broad ancestry increases the risk of incorrect wrapping.
* Cleanup — the Shell must remove wrappers on `removeChild` so unmounted overlays do not leave dangling scope sections.

== Debugging

* Inspect the trigger accessor in the console (Shell exposes it via the initializer): it should point at the last hovered or focused element for gesture-driven overlays.
* Inspect an overlay node before and after insertion: intermediate `data-intermediate-style-*` attributes should appear when creation helpers run and be promoted to `data-style-*` after the Shell body hook runs.
* Inspect wrappers: the wrapper element should carry `data-style-id` and `data-style-isolation` when the Shell promoted the attribution.
