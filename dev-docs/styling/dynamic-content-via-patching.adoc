== Question answered

How does an overlay or dialog that renders *outside* the app's scope still pick up the right style data when OneCX patches it at creation time, and how are wrapping and cleanup handled once the node reaches `document.body`?

== Why it exists

The {scope_at_rule} model (link:{u8}[Unit 8]) confines an app's rules to the DOM subtree that carries its `data-style-id`. Overlays and dialogs — PrimeNG dialogs, CDK popups, PrimeReact dropdowns, tooltips — are often created outside that subtree, so they would otherwise receive no scoped rules and look broken.

Creation-time patching solves that by recovering the owning app from the most recent trigger element, copying the resolved style data onto the node that is about to be inserted, and letting the Shell's body wrapper promote that data into a scoped wrapper as the node is appended. This page covers that patching route end to end. The companion option, which keeps the out-of-scope content inside an app-owned container instead of patching the portal child directly, is link:{u7}[Dynamic content via container].

== How it works

Two pieces work together: a trigger-element lookup that resolves the app's style data, and a creation-time patch that stamps the portal child before it reaches the DOM.

=== The trigger element

The trigger element is the element under the pointer or under focus. The Shell tracks it continuously: `initializeOnecxTriggerElementListener` in link:{shell}/src/app/shell/utils/styles/onecx-trigger-element.utils.ts[`onecx-trigger-element.utils.ts`] attaches `mouseover` and `focusin` handlers to `document`; on each event it stores `event.target` on the page-global `window.onecxTriggerElement`. A plain read of that global is the accessor on the React side — `getOnecxTriggerElement` in link:{libs}/react-utils/src/lib/styling/primeReact/dynamicScoping/functions/onecx-trigger-element.ts[`onecx-trigger-element.ts`] returns `globalThis.onecxTriggerElement`, typed by `onecxTriggerElement: EventTarget | null` in link:{libs}/react-utils/src/lib/styling/primeReact/dynamicScoping/functions/declarations.ts[`declarations.ts`].

Because `window.onecxTriggerElement` is a single page-global, attribution always reflects the most recent interaction. That is deliberate: the overlay opens in response to a user gesture, so the last hovered or focused element is the best available owner for gesture-driven overlays.

=== The closest-ancestor walk

From the trigger element, the mechanism climbs the DOM to the nearest ancestor that carries a scope marker and reads the app's style data from it.

* `findElementWithStyleDataOrIntermediateStyleData(startNode)` walks `parentElement` upward until it finds an element whose `dataset` holds a `styleId` (`data-style-id`) or an `intermediateStyleId` (`data-intermediate-style-id`); if it reaches the top without one it returns `null`. Both frameworks implement this identically — link:{libs}/react-utils/src/lib/styling/primeReact/dynamicScoping/functions/findElementWithStyleDataOrIntermediateStyleData.ts[`findElementWithStyleDataOrIntermediateStyleData.ts`] (React) and the same-named function in link:{libs}/angular-utils/style/src/utils/dom-style.utils.ts[`dom-style.utils.ts`] (Angular).
* `getStyleDataOrIntermediateStyleData(element)` calls that walk and, on the element it finds, reads `dataStyleIdKey` / `dataNoPortalLayoutStylesKey` / `dataMfeElementKey` (falling back to the `dataIntermediate*` keys). It returns a `StyleData` object, or `null` when no scoped ancestor exists.

The marker keys are the ones listed in link:{libs}/react-utils/src/lib/utils/styleAttributes.ts[`styleAttributes.ts`] (React) and link:{libs}/angular-utils/src/lib/utils/scope.utils.ts[`scope.utils.ts`] (Angular): `data-style-id` opens the scope section for a `productName|appId`, and the `data-intermediate-style-id` family is the short-lived marker an element carries while it is being placed.

The result of the walk is what gets written onto the overlay's content so the eventual wrapper or patched node can participate in the owning app's scope. The attribute model, the `@scope` blocks they feed, and the `to ([data-style-isolation])` boundary are described in link:{u3}[Unit 3]; this page covers how that attribution is applied at creation time, while the Shell's body wrapper handles the eventual patch/body-wrapper path.

=== Creation-time patching

React patches `ReactDOM.createPortal` through `ensurePrimereactDynamicDataIncludesIntermediateStyleData` in link:{libs}/react-utils/src/lib/styling/primeReact/dynamicScoping/index.ts[`dynamicScoping/index.ts`]. The patch inspects the portal's child and then its nested child, because the actual PrimeReact element is one level below the portal wrapper. When that nested child exists and its `className` includes `p-`, the patch clones that child with the intermediate style data returned by `getOnecxTriggerElement` → `getStyleDataOrIntermediateStyleData`, using `appendIntermediateStyleData` to write the `data-intermediate-style-*` markers.

The important detail is what it does *not* touch: the portal target or container remains unchanged. Only the PrimeReact child is cloned and stamped, so the creation-time patch works without changing where the portal renders.

Once that patched child is appended, the Shell's body wrapper can recognize the intermediate markers, promote them to permanent `data-style-*` attributes, and wrap or clean up the node as needed.

== Angular / React

The *read* side — the trigger element plus closest-ancestor walk — is the same in both frameworks. What differs is how the dynamic content gets onto the page and which styles are framework-owned.

=== Angular

Angular component CSS stays Angular-encapsulated. The Angular compiler already scopes component styles to the component, so this page is *not* where Angular component CSS is re-written. The Shell-side PrimeNG variable prefix handling is a separate path and is described in link:./angular-component-styles.adoc[Angular component styles].

For dynamic content, Angular CDK still renders overlays into its container, and OneCX can reparent that container into the app-owned dynamic container so the overlay inherits the scope. That container path is the companion option documented in link:{u7}[Dynamic content via container].

=== React

React has no overlay container to reparent. Instead, the `createPortal` patch above stamps the PrimeReact child directly at creation time. The portal target stays untouched, and the wrapper logic later promotes the intermediate markers when the node is inserted.

`attachPrimeReactScoper` in link:{libs}/react-utils/src/lib/styling/primeReact/scopingFunctionality/index.ts[`scopingFunctionality/index.ts`] is separate again: it watches PrimeReact style content in `document.head` and scopes PrimeReact CSS blocks. It does *not* stamp portal containers, and it does *not* handle Angular component CSS.

== Edge cases & pitfalls

* *Stale trigger element.* `window.onecxTriggerElement` is a single global holding the last hovered or focused element. An overlay opened programmatically — with no recent pointer or focus inside the owning app — may be attributed to whichever app was interacted with most recently, or to nothing. The Shell's `getOnecxTriggerElement` fallback narrows this, but a global gesture cannot infer the owner of a code-driven overlay.
* *Trigger outside any scope.* If the trigger element has no scoped ancestor, the walk returns `null` and the overlay is left unattributed — it receives no app styles.
* *Portal child not PrimeReact.* The React patch only clones the nested child when its class name includes `p-`. If the portal child is not a PrimeReact node, the patch does nothing and the body wrapper sees the original node.
* *The portal target stays unchanged.* The creation-time patch stamps the child, not the portal container. If the container itself gets mutated, that is a different path and a bug.
* *Cleanup still matters.* Even with creation-time patching, the Shell must remove wrappers on `removeChild` so an unmounted overlay does not leave a dangling scope section behind.
* *PrimeReact styles are separate.* `attachPrimeReactScoper` scopes PrimeReact style blocks in `document.head`; it does not participate in Angular component CSS or in the portal-child patch.

== Debugging

In the devtools:

* Evaluate `window.onecxTriggerElement` in the console: it should be the element you last hovered or focused (the thing that opened the overlay). `null` means no gesture has set it yet.
* Inspect the portal child before and after insertion: the cloned PrimeReact child should gain `data-intermediate-style-*` attributes, and those should be promoted to `data-style-*` once the body wrapper runs.
* Inspect the overlay container or wrapper: the eventual wrapper should carry `data-style-id="<productName|appId>"` and `data-style-isolation`. A raw overlay with no such ancestor is not scoped.
* Look for `style[data-app-primereact-style="<id>"]` in the `<head>` only when debugging PrimeReact CSS. That is where `attachPrimeReactScoper` writes scoped PrimeReact rules; it is independent of the portal-child patch.

General runtime inspection is covered by the *Diagnostics* Area.
