== Question answered
How does an overlay or dialog that renders outside an app's scoped subtree still pick up that app's style data when OneCX intercepts creation, and how are wrapping and cleanup handled once the node reaches document.body?

== Why it exists
The {scope_at_rule} model (link:{u8}[Unit 8]) confines an app's rules to the DOM subtree that carries its data-style-id. Overlays and dialogs are frequently created outside that subtree and therefore need attribution and a body-time promotion step so they receive the correct scoped styles.

This Unit documents the framework-agnostic creation-time interception contract, the Libs-side and Shell-side responsibilities, the Shell append-to-body flow (wrapping/blacklisting), cleanup behaviour, and common edge cases. The container-based alternative is link:{u7}[Dynamic content via container].

== How it works
Two responsibilities cooperate:

* Libs-side: resolve the owning app from the current trigger element and stamp intermediate style attributes onto the semantic content node(s) at creation time.
* Shell-side: observe body mutations, promote intermediate attributes into permanent data-style-* markers or wrappers, and clean up when nodes are removed.

=== Inventory of document-level helpers
Several document-scoped helpers exist to provide compatibility or to surface a single creation helper for apps:

* document.createElementFromPrimeNg (deprecated compatibility hook) — used historically by PrimeNG shims. Apps/rewrite rules should no longer rely on it.
* document.createElementFromMaterial (deprecated compatibility hook) — Angular Material compatibility shim; deprecated in favour of the generic helper.
* document.createOnecxElement (generic creation helper) — the recommended, framework-agnostic helper apps or lib shims call to stamp data-intermediate-style-* attributes onto newly created semantic nodes before insertion.
* document.createOnecxDynamicContainer (container helper) — creates a namespaced dynamic container element; related to Unit 7's container flow and not required for patching-based attribution.

(PrimeNG/Material-specific wrappers remain for compatibility; prefer createOnecxElement where possible.)

== Libs side (app / library helpers)
Libs or apps are expected to call a small creation helper at the point where overlays/portals are constructed. Key responsibilities:

* Resolve the StyleData by reading the current trigger element (Shell accessor) immediately before insertion.
* Stamp the semantic content node(s) with short-lived data-intermediate-style-* attributes (id, isolation, optional MFE metadata).
* Only mutate semantic nodes that will be observed by the Shell; avoid touching unrelated portal root containers.

Example integration note: build-time rewrites (see the reviewed example) adjust library creation calls (PrimeNG/Angular Material) to invoke the Shell-provided creation helper, not to patch arbitrary app code. See the reviewed app-side webpack example for onecx-help-ui for how rewriting is applied. link:docs/modules/onecx-portal-ui-libs/pages/migrations/angular-19/update-webpack-config.adoc[App webpack rewrite example]

== Shell side (runtime helpers & body hooks)
The Shell implements the accessor, body hooks, and wrapper utilities. Implementers should call the Shell helpers below (linked to their defining source) when explaining or tracing behaviour.

Shell helpers (linked):
* initializeOnecxTriggerElementListener — installs `mouseover` / `focusin` handlers and exposes the current trigger element. link:{shell}/src/app/shell/utils/styles/dynamic-content-initializer.utils.ts[`dynamic-content-initializer.utils.ts`]
* getOnecxTriggerElement — accessor and fallback logic that resolves the last trigger element or searches for a `.onecx-body` descendant. link:{shell}/src/app/shell/utils/styles/onecx-trigger-element.utils.ts[`onecx-trigger-element.utils.ts`]
* appendIntermediateStyleData / appendStyleData — map a StyleData object onto an element's `data-intermediate-style-*` or `data-style-*` attributes. link:{shell}/src/app/shell/utils/styles/style-data.utils.ts[`style-data.utils.ts`]
* createWrapper / findStyleDataWrapper / wrapWithDiv — wrapper creation and lookup used to group appended nodes under a `data-style-id` boundary. link:{shell}/src/app/shell/utils/styles/style-data.utils.ts[`style-data.utils.ts`], link:{shell}/src/app/shell/utils/styles/body-overwrites.utils.ts[`body-overwrites.utils.ts`]
* ensureBodyChangesIncludeStyleData (body hook) — appendChild/removeChild interception that promotes intermediate markers on append and removes wrappers on removal. link:{shell}/src/app/shell/utils/styles/body-overwrites.utils.ts[`body-overwrites.utils.ts`]
* observeStyleDataWrapper / removeStyleDataRecursive — observe wrapper lifecycle and remove stale style sections. link:{shell}/src/app/shell/utils/styles/body-overwrites.utils.ts[`body-overwrites.utils.ts`]
* dynamicContentInitializer / dynamicContentUtils — initializer and small utilities coordinating trigger/listener startup and helper wiring. link:{shell}/src/app/shell/utils/styles/dynamic-content-initializer.utils.ts[`dynamic-content-initializer.utils.ts`], link:{shell}/src/app/shell/utils/styles/dynamic-content.utils.ts[`dynamic-content.utils.ts`]

== Body append/blacklist & CDK overlays
The Shell body hook inspects nodes appended to document.body and either:

* Promotes intermediate attributes to permanent data-style-* markers and wraps the node in a scoped wrapper when required; or
* Leaves nodes untouched when they match a configured blacklist (elements that must not be wrapped). The blacklist includes known host nodes for non-UI runtime code and may be extended conservatively.

Note: when using CDK overlays (Angular CDK), the same creation-time stamping applies; the build-time rewrite ensures CDK overlay creation calls are rewritten to the Shell helper in reviewed app configurations.

== Edge cases & pitfalls
* Stale trigger element — programmatic or delayed insertions risk attribution to an outdated trigger. Libs should resolve the trigger immediately before insertion.
* No scoped ancestor — when no resolved StyleData exists the overlay remains unattributed.
* Over-stamping — avoid stamping parent portal roots; only stamp the semantic content nodes.
* Cleanup — Shell must remove wrappers on removeChild to prevent orphaned style sections.
