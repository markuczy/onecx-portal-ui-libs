= Topic System

== Overview

Topics are the cross-context messaging layer that powers shell-to-MFE and MFE-to-shell communication. Every topic is an instance of `Topic<T>` from `@onecx/accelerator` — it publishes typed values and makes them available as an RxJS `Observable<T>` to all subscribers, even across browser tabs and iframes.

The pattern solves a fundamental problem: in a Module Federation architecture, the shell and MFEs live in different JavaScript contexts. Topics bridge that gap using `window.postMessage` and `BroadcastChannel`.

Each topic is identified by a `(name, version)` pair and carries a single type `T`. Subscribers never need to know where a value came from — they subscribe to the topic and react to changes.

== Architecture

=== Message Flow

When Topic A publishes a value, the sequence is:

. Topic A calls `publish(value)`.
. A `TopicNext` message carrying the value is sent via `postMessage` or `BroadcastChannel`.
. A `TopicResolve` message is queued immediately after.
. All Topic instances listening on `window` (or BroadcastChannel) receive `TopicNext`.
. If an instance matches `(name, version)` and the value is newer, it updates its internal `BehaviorSubject`.
. The publisher's instance receives `TopicResolve`, resolves the stored promise, and `publish()` returns.

The promise returned by `publish()` only resolves after all instances have processed `TopicNext`, because both messages are queued sequentially and the event loop processes them in order.

=== Transport

A topic uses three transport channels:

[cols="1,2"]
|===
| Channel | Purpose

| `window.postMessage` | Cross-context messaging — works between iframes and tabs. Always available.
| `BroadcastChannel` (V1) | Same-origin cross-tab messaging on a named channel (`Topic-name|version`). Falls back from window events when detected.
| `BroadcastChannel` (V2) | Same-origin per-tab messaging (`TopicV2-name|version-tabId`). Reduces cross-talk between tabs.
|===

The system prefers BroadcastChannel V2 when enabled, falls back to BroadcastChannel V1, and ultimately relies on `window.postMessage`. When a message arrives via `window`, BroadcastChannel is disabled for that topic to avoid dual delivery.

=== Message Types

Three message types exist:

[cols="1,2,3"]
|===
| Type | Class | Purpose

| `TopicNext` | `TopicDataMessage<T>` | Broadcasts a new value. Contains the payload `data: T`.
| `TopicGet` | `TopicMessage` | Requests current state. Sent by a new topic instance on construction. Initialized instances respond with their latest `TopicNext`.
| `TopicResolve` | `TopicResolveMessage` | Acknowledges a publish. Contains the `resolveId` of the original `TopicNext` message, used to resolve the publisher's promise.
|===

All messages extend the `Message` base class, which provides:

* `timestamp` — `performance.now()` or `Date.now()`, used for ordering.
* `id` — a globally incrementing counter on `globalThis.onecxMessageId`, used for deterministic ordering when timestamps collide.

=== Ordering

Messages are ordered by timestamp first, then by `id`. When a topic receives `TopicNext`, it only updates if:

* No value exists yet, OR
* The incoming `id` is greater than the current `id`, OR
* The incoming `timestamp` is greater than the current `timestamp`.

== Topic Class

*File:* `libs/accelerator/src/lib/topic/topic.ts`

=== Constructor

[source,typescript]
----
constructor(name: string, version: number, sendGetMessage = true)
----

[cols="1,2"]
|===
| `name` | The topic name (e.g. `'permissions'`, `'currentTheme'`).
| `version` | The API version (always `1` for current topics).
| `sendGetMessage` | Whether to send a `TopicGet` on construction. Set to `false` for RPC-style topics where the subscriber initiates.
|===

On construction:

. Creates a `BehaviorSubject<TopicDataMessage<T> | undefined>` for internal state.
. Registers a `window` message listener.
. Optionally sets up `BroadcastChannel` readers (V1 and V2).
. If `sendGetMessage` is `true`, sends a `TopicGet` (with a 100ms delay if many topics start simultaneously within 2 seconds of the accelerator init date).

=== Core API

[cols="1,2"]
|===
| `isInitialized` | A `Promise<void>` that resolves when the topic has received its first value.

| `asObservable()` | Returns `Observable<T>` filtered to only emit after initialization.

| `subscribe(...)` | RxJS subscription to receive values.

| `pipe(...)` | RxJS pipe for operators — chains through `asObservable()`.

| `destroy()` | Cleans up event listeners and BroadcastChannel instances.
|===

=== TopicPublisher Base

*File:* `libs/accelerator/src/lib/topic/topic-publisher.ts`

`Topic` extends `TopicPublisher`, which provides the `publish()` method:

[source,typescript]
----
publish(value: T): Promise<void>
----

The `TopicPublisher` class can also be used standalone when only publishing is needed (no subscription), such as for RPC-style requests where a response is expected back on a separate topic.

=== SyncableTopic (Deprecated)

*File:* `libs/accelerator/src/lib/topic/syncable-topic.ts`

Provides synchronous access via `getValue()`. Deprecated — reading async data synchronously is unsafe. Use `Topic` with RxJS patterns instead.

== Topics in the Integration Interface

All concrete topics live in `libs/integration-interface/src/lib/topics/`. Each topic defines a specific communication channel between the shell and MFEs.

=== Navigation and Routing

[cols="1,2,3"]
|===
| Topic | Payload | Purpose

| `CurrentLocationTopic` | `CurrentLocationTopicPayload` | Tracks the current URL and whether it is the first navigation. Published by the shell on navigation.
| `CurrentMfeTopic` | `MfeInfo` | Identity of the currently active MFE (appId, productName, mountPath, baseHref). Published by the shell when an MFE loads.
| `CurrentPageTopic` | `PageInfo` | The current page within the active MFE (path, pageName, helpArticleId). Includes a `MutationObserver` to detect DOM-based path changes.
| `CurrentWorkspaceTopic` | `Workspace` | The active workspace/portal, including routes, endpoints, and MFE registrations. Topic name is `'currentPortal'`.
|===

`CurrentPageTopic` overrides `asObservable()` to filter out values when the page path doesn't match `document.location.pathname`, ensuring consumers only see values relevant to the current browser URL.

=== Appearance and Theming

[cols="1,2,3"]
|===
| Topic | Payload | Purpose

| `CurrentThemeTopic` | `Theme` | The active theme with assets, CSS, and overrides. Deprecated — use `CurrentThemesTopic`.
| `CurrentThemesTopic` | `CurrentThemes` | Multi-version theme with properties, fonts, and version list. The current theming topic.
|===

=== Security and Configuration

[cols="1,2,3"]
|===
| Topic | Payload | Purpose

| `ConfigurationTopic` | `Config` (`Record<string, string>`) | Key-value configuration delivered by the shell. Published once at startup.
| `IsAuthenticatedTopic` | `void` | Signals when the user becomes authenticated. Used to gate authentication-dependent initialization.
| `PermissionsTopic` | `string[]` | The current permission set. Published by the shell when permissions change.
| `PermissionsRpcTopic` | `PermissionsRpc` | RPC-style topic (no `sendGetMessage`). MFEs publish a request with `appId` and `productName`; the shell responds with permissions on the same topic.
| `ParametersTopic` | `ParametersTopicPayload` | Application parameters keyed by `productName` and `appId`. Delivered by the shell.
|===

=== User Context

[cols="1,2,3"]
|===
| Topic | Payload | Purpose

| `UserProfileTopic` | `UserProfile` | User profile data (email, firstName, lastName, etc.). Published by the shell.
|===

=== UI Communication

[cols="1,2,3"]
|===
| Topic | Payload | Purpose

| `GlobalErrorTopic` | `string` | Displays a global error message. Published by MFEs, consumed by the shell's error UI.
| `GlobalLoadingTopic` | `boolean` | Shows or hides the global loading indicator. Published by MFEs.
| `MessageTopic` | `Message` | In-app messages with severity, summary, and detail. Published by MFEs, rendered by the shell.
| `NotificationTopic` | `Notification` | Toast-style notifications. Published by MFEs, rendered by the shell.
|===

=== Events

[cols="1,2,3"]
|===
| Topic | Payload | Purpose

| `EventsTopic` | `TopicEventType` | General-purpose event bus. Supports `NAVIGATED` and `AUTH_LOGOUT_BUTTON_CLICKED` events. No `sendGetMessage` — only push events.
|===

=== Remote Components and Resizing

[cols="1,2,3"]
|===
| Topic | Payload | Purpose

| `RemoteComponentsTopic` | `RemoteComponentsInfo` | Delivers remote component metadata and slot mappings from the shell.
| `ResizedEventsTopic` | `TopicResizedEventType` | Slot resize events with optional event filtering via `requestEvent()`. Supports `SLOT_RESIZED`, `SLOT_GROUP_RESIZED`, and `REQUESTED_EVENTS_CHANGED`.
|===

`ResizedEventsTopic` extends `Topic` with selective publishing — it only publishes resize events for entities that have registered interest via `ResizedEventsTopic.requestEvent()`. Unregistered entities are silently dropped.

=== Assets

[cols="1,2,3"]
|===
| Topic | Payload | Purpose

| `IconTopic` | `Icon` | RPC-style icon requests. MFEs publish `IconRequested`; the shell responds with `IconsReceived`. No `sendGetMessage`.
| `ImageRepositoryTopic` | `ImageRepository` | Image repository data. Published by the shell.
|===

=== Translations

[cols="1,2,3"]
|===
| Topic | Payload | Purpose

| `DynamicTranslationsTopic` | `DynamicTranslationsMessage` | RPC-style translation requests. MFEs publish `TranslationsRequested` with locale and contexts; the shell responds with `TranslationsReceived`. No `sendGetMessage`.
|===

== Usage Patterns

=== Subscribing to a Topic

[source,typescript]
----
// Create the topic — it automatically syncs with any existing instance
const permissions = new PermissionsTopic()

// Wait for initialization
await permissions.isInitialized

// Subscribe for reactive updates
permissions.subscribe((perms) => {
  console.log('Permissions:', perms)
})

// Use with RxJS operators
this.data$ = permissions.pipe(
  map(perms => perms.includes('admin'))
)
----

=== Publishing to a Topic

[source,typescript]
----
const loading = new GlobalLoadingTopic()

// Show loading
await loading.publish(true)

// Hide loading
await loading.publish(false)
----

=== RPC Pattern (Request-Response)

For RPC-style topics like `PermissionsRpcTopic`, the subscriber initiates by publishing a request and listening for the response:

[source,typescript]
----
const rpc = new PermissionsRpcTopic()  // sendGetMessage = false

// Publish a request
rpc.publish({ appId: 'my-app', productName: 'my-product' })

// Listen for the response
rpc.pipe(
  filter(m => m.appId === 'my-app' && m.productName === 'my-product')
).subscribe((response) => {
  console.log('Permissions:', response.permissions)
})
----

The `sendGetMessage = false` constructor argument prevents the topic from requesting initial state, because there is no state to sync — each message is an independent request-response pair.

=== Cleaning Up

Call `destroy()` when a topic is no longer needed (e.g., in `ngOnDestroy`):

[source,typescript]
----
ngOnDestroy(): void {
  this.remoteComponentsTopic.destroy()
}
----

This removes the `window` event listener and closes BroadcastChannel instances.
