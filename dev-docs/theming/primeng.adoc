= PrimeNG Theming Integration

:idprefix:
:idseparator:

This document explains how ONECX theming integrates with PrimeNG's design token system, how to configure an MFE for theme support, and how to choose between v1 and v2 theming.

[#primeng-design-tokens]
== PrimeNG Design Tokens

Since version 19, PrimeNG uses a design token theming model. Components reference design tokens (e.g. `{semantic.colorScheme.light.content.background}`) rather than hardcoded CSS values. A **preset** is a JavaScript object that defines all token values; `PrimeNG.setThemeConfig()` applies it at runtime.

ONECX bridges its theme system to this model: theme variables → PrimeNG preset → rendered components.

[#onecx-and-primeng-theming]
== ONECX Theming With PrimeNG

ONECX provides two integration paths depending on the theme version:

[cols="1,3"]
|===
| Path | How it works

| v1 (legacy)
| Theme variables are read into a `ThemeConfig` object which updates an extended `onecx` section of the PrimeNG preset. Primary palette is regenerated. Applied via `PrimeNG.setThemeConfig()`.

| v2 (structured)
| `ThemePropertiesV2` is resolved (theme references expanded), mapped through `MAPPING_RULES` into a PrimeNG preset shape, merged with overrides, and applied via `PrimeNG.setThemeConfig()`. Custom CSS rules complement preset tokens where PrimeNG has no equivalent.
|===

xref:concept.adoc#theme-versions[See Theme Versions] for a comparison of v1 and v2 theme structures.

[#providing-theme-config]
== Configuring an MFE for Theming

Every MFE or remote component must provide theme configuration via `provideThemeConfig()`:

[source,ts]
----
// app.module.ts or app.config.ts
import { provideThemeConfig } from '@onecx/angular-utils/theme/primeng'

provideThemeConfig({
  maxVersion: 2,              // Use v2 mapping pipeline (default: 1)
  isAdvancedTheming: true,    // Enable workspace-level PrimeNG overrides (default: false)
  overrides: myOverrides,     // Application-level PrimeNG token overrides
  cssOverrides: myCss,        // Application-level CSS string overrides
})
----

[cols="1,2"]
|===
| Option | Description

| `maxVersion`
| Maximum theme version to use. If the theme provides v2 data and `maxVersion >= 2`, v2 mapping is used. Falls back to v1 if `maxVersion` is 1. Default: 1.

| `isAdvancedTheming`
| When `true`, workspace-level PrimeNG overrides (`OverrideType.PRIMENG`) are parsed and merged into the preset. When `false`, they are ignored. Default: `false`.

| `overrides`
| Application-level PrimeNG token overrides. Can be a static object, a Promise, or a function returning either. Merged on top of the mapped preset.

| `cssOverrides`
| Application-level CSS string overrides. Can be a string, a Promise\<string\>, or a function returning either. Appended to the theme CSS.
|===

`provideThemeConfig()` registers the following internally:

* `provideAnimationsAsync()` -- Angular async animations
* `providePrimeNG({})` -- PrimeNG configuration
* `ThemeConfigService` -- subscribes to theme changes and applies them
* `CustomUseStyle` -- replaces PrimeNG's default `UseStyle` for per-MFE style scoping
* `AppStylesInitializer` -- initializes application styles

[#theme-config-service]
== ThemeConfigService

`ThemeConfigService` is the core runtime service. It subscribes to `CurrentThemesTopic` and applies themes on every change.

.Theme application flow for v2
[.ascii-diagram]
....
  CurrentThemesTopic emits
         │
         ▼
  Check themeVersionAvailable(2)
         │
    ┌────┴────┐
    │   v2?   │
    └────┬────┘
         │ Yes
         ▼
  getThemeProperties()
  ─ Resolve region overrides
    (for remote components: merge region primitives/usages)
         │
         ▼
  mapThemeToPreset(properties)
  ─ Resolve theme refs
  ─ Apply mapping rules → preset variables
  ─ Generate CSS rules → css string
         │
         ▼
  generateThemeOverrides(overrides)
  ─ Parse PrimeNG overrides (if advanced theming)
  ─ Fold into single object
         │
         ▼
  mergeDeep(preset, overrides)
         │
         ▼
  PrimeNG.setThemeConfig({
    theme: {
      preset: { ...merged, css: cssFromTheme + cssOverrides },
      options: { darkModeSelector: 'system' },
    },
  })
         │
         ▼
  ensureStyles() → inject scoped CSS into <head>
....

.For v1, the flow is simpler: load `CustomPreset`, construct `ThemeConfig` from flat variables, merge with overrides, apply.

[#version-selection]
== Version Selection

The system determines which theme version to use through a negotiation:

. The Shell publishes `versions` array (e.g. `[1, 2]`) with the theme data.
. The MFE has a `maxVersion` preference (from `provideThemeConfig` options or `THEME_MAX_VERSION` token).
. `themeVersionAvailable(version, injector)` checks if the requested version is in the published `versions` array.
. If v2 is available and requested, v2 mapping is used. Otherwise, v1 is used.
. If neither is available, an error is thrown.

This means an MFE can declare `maxVersion: 2` and safely fall back to v1 if the backend only provides v1 data.

[#custom-preset-v1]
== OneCX Custom Preset (v1)

The v1 preset is defined in link:../../libs/angular-utils/theme/primeng/src/preset/custom-preset.ts[custom-preset.ts] and consists of:

* **Preset variables** -- Default token values for all PrimeNG components.
* **OneCX extend section** -- Theme variables exposed as design tokens in the `onecx` namespace.
* **Default theme variables** -- Fallback values used when no workspace theme is loaded.

Custom OneCX tokens in the extend section:

[cols="1,1,1"]
|===
| Token | Design Token | CSS Variable

| `errorColor`
| `{onecx.error.color}`
| `--p-onecx-error-color`

| `contentBgColor`
| `{onecx.content.bg.color}`
| `--p-onecx-content-bg-color`
|===

[#advanced-theming]
== Advanced Theming

When `isAdvancedTheming` is enabled, workspace administrators can define PrimeNG-level overrides that target specific design tokens. These overrides are published as `ThemeOverride` objects with `type: OverrideType.PRIMENG` and a JSON `value`.

The service:

. Filters overrides by `PRIMENG` type.
. Parses the `value` JSON string.
. Deep-merges all overrides into a single object.
. Merges the result on top of the mapped preset.

xref:theme-overrides.adoc[See Theme Overrides] for details on how overrides are scoped and applied.

[#style-scoping]
== Style Scoping (CustomUseStyle)

`CustomUseStyle` replaces PrimeNG's default `UseStyle` service to ensure per-MFE style isolation:

. All PrimeNG style sheets are scoped using `@scope` rules and prefixed CSS variable names.
. Theme override styles are appended as the last style sheet in `<head>`, ensuring they take precedence via CSS specificity.
. For remote components, styles are scoped by slot name.
. For MFEs, styles are scoped by product/app identity.

xref:../styles/primeng-integration.adoc[See PrimeNG Integration] for technical details.

[#webpack-modifications]
== Shell Webpack Modifications

The Shell's webpack configuration applies source modifications at build time:

. `document.createElement(` in PrimeNG → replaced with `document.createElementFromPrimeNg(...)` to inject scope data into dynamically created elements.
. `Theme.setLoadedStyleName` → replaced with a no-op to prevent unwanted theme recomputations.
. `document.createElement('style'` in `@angular/platform-browser` → replaced with `document.createElementFromSharedStylesHost(...)` for Angular component style scoping.
