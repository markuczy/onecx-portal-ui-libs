= Theming Concept

:idprefix:
:idseparator:

This document provides a conceptual and technical overview of theming in ONECX. After reading, you should be able to:

* Understand what a theme is and how v1 and v2 themes differ.
* Know how themes flow from the backend through the Shell to MFEs.
* Understand how dark mode is supported.
* Use theme variables in your styles.

[#what-is-a-theme]
== What Is a Theme

A **theme** is a collection of design tokens that define the visual appearance of an application -- colors, typography, spacing, borders, shadows, and component-specific styling.

Each **Workspace** has one active theme. When a user switches workspaces, the active theme changes, and all UI components update to reflect the new appearance. The same code produces different looks depending on the workspace.

[#theme-versions]
== Theme Versions

ONECX supports two theme versions that can coexist:

[cols="1,3"]
|===
| Version | Description

| v1
| Flat key-value pairs of CSS custom properties (e.g. `--primary-color: #3B82F6`). Simple but unstructured -- any application can define arbitrary variable names. Still supported for backwards compatibility.

| v2
| Structured token tree with primitives (foundational design tokens) and usages (component-specific tokens). Validates against a Zod schema, supports theme references (`{{primitives.font.family}}`), dual-mode colors (`{ light, dark }`), and region overrides. Maps to PrimeNG presets via a deterministic pipeline.
|===

[cols="1,2"]
|===
| v1 example
| `ThemeProperties = { "primary-color": "#3B82F6", "font-family": "Inter" }`

| v2 example
| `ThemePropertiesV2 = { primitives: { font: { family: "Inter" }, variant: { primary: { bg: "#3B82F6" } } }, usages: { table: { ... } } }`
|===

The backend stores both versions side by side. The Shell publishes a `versions` array (`[1]`, `[2]`, or `[1, 2]`) alongside theme data so MFEs can determine which version to use.

[#theme-lifecycle]
== Theme Lifecycle

.A theme flows from backend to rendered UI in five stages:
[.ascii-diagram]
....
  Backend                      Shell                       CurrentThemesTopic              MFE
  (BFF)                       (theme-apply)              (BroadcastChannel)           (ThemeConfigService)

    │                           │                            │                           │
    │  1. Theme object          │                            │                           │
    │  ──────────────────────►  │                            │                           │
    │  { properties: { v1, v2 },│                            │                           │
    │    overrides: [...],      │                            │                           │
    │    versions: [1, 2] }     │                            │                           │
    │                           │                            │                           │
    │                           │  2. Validate v2 with Zod   │                           │
    │                           │  3. Set CSS vars on <html> │                           │
    │                           │  4. Publish to topic       │                           │
    │                           │  ────────────────────────►  │                           │
    │                           │                            │                           │
    │                           │                            │  5. Subscribe             │
    │                           │                            │  ───────────────────────►  │
    │                           │                            │                           │  6. Map to preset
    │                           │                            │                           │  7. Apply overrides
    │                           │                            │                           │  8. PrimeNG.setThemeConfig()
    │                           │                            │                           │
....

.Stages
[cols="1,3"]
|===
| 1. Backend publishes theme
| The BFF provides a `Theme` object containing `properties` (v1 and/or v2), `overrides` (per-application token overrides), and `versions` (supported version numbers).

| 2. Shell parses and validates
| `ThemeApplyService.applyTheme()` detects v2 data (presence of `"usages"` key), validates with Zod `themeSchema.safeParse()`, and determines the `receivedThemeVersions` array.

| 3. Shell injects CSS variables
| `applyThemeV2Variables()` recursively walks the v2 theme object and sets CSS custom properties on `document.documentElement`. Every path becomes a variable: `primitives.font.family` → `--onecx-theme-primitives-font-family`. See xref:theme-v2.adoc#shell-css-variable-injection[CSS Variable Injection] for details.

| 4. Shell publishes to topic
| The parsed theme is published via `CurrentThemesTopic` (BroadcastChannel), making it available to all MFEs and remote components on the page. The legacy `currentTheme$` observable is also emitted for backwards compatibility.

| 5. MFE subscribes
| `ThemeConfigService` in each MFE subscribes to `themeService.currentThemes$`.

| 6. MFE maps and applies
| For v2: `mapThemeToPreset()` transforms the theme into a PrimeNG preset. For v1: `ThemeConfig` constructs a preset from flat variables. Overrides are merged, then `PrimeNG.setThemeConfig()` applies the result.
|===

[#dark-mode]
== Dark Mode

v2 themes support light/dark mode through dual-mode color values:

[source,typescript]
----
// In a theme definition
{
  primitives: {
    variant: {
      primary: {
        bg: { light: "#3B82F6", dark: "#60A5FA" }
      }
    }
  }
}
----

The Shell injects three CSS custom properties for each dual-mode value:

[source,css]
----
--onecx-theme-primitives-variant-primary-bg-color-light: #3B82F6;
--onecx-theme-primitives-variant-primary-bg-color-dark: #60A5FA;
--onecx-theme-primitives-variant-primary-bg-color: light-dark(
  var(--onecx-theme-primitives-variant-primary-bg-color-light),
  var(--onecx-theme-primitives-variant-primary-bg-color-dark)
);
----

The `color-scheme: light dark` property is set on `<html>`, enabling the CSS `light-dark()` function which automatically resolves based on the user's OS preference.

PrimeNG is configured with `darkModeSelector: 'system'`, so PrimeNG components follow the system preference automatically.

[#using-theme-variables]
== Using Theme Variables in Styles

When creating styles for UI components, use theme variables rather than hardcoded values:

[source,css]
----
// v1: direct CSS custom property
button {
  background-color: var(--primary-color);
}

// v2: CSS variable generated from theme path
button {
  background-color: var(--onecx-theme-primitives-variant-primary-bg-color);
}

// v2: via PrimeNG design token
button {
  background-color: var(--p-content-background);
}
----

A complete list of v1 theme variables is available in the ONECX documentation. For v2, every token in the `ThemePropertiesV2` schema has a corresponding CSS variable on `<html>`.

[#theme-overrides-at-a-glance]
== Theme Overrides (Overview)

Workspace administrators can define per-application theme overrides that merge on top of the base theme. These are published as part of the `overrides` array in the theme object. Each override has a `type` (`CSS` or `PRIMENG`) and a `value` (JSON string).

xref:theme-overrides.adoc[See Theme Overrides] for technical details.

[#where-are-defaults-defined]
== Default Theme Variables

Before a workspace theme loads, default values are available:

* **v1 defaults**: Defined in link:../../libs/portal-layout-styles/src/styles/shell/theme_defaults.scss[theme defaults stylesheet], imported by the Shell's global stylesheet.
* **v2 defaults**: Defined in usage schemas as theme references (e.g. `{{primitives.font.family}}`), resolved through the mapping pipeline.

This ensures the UI is never unstyled during workspace loading.
