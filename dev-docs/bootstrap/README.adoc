= Application Bootstrap
:idprefix:
:idseparator: -

This Area covers the path from the Shell's `index.html` to a running App or Remote Component. It is the "cold start" of every OneCX page: how the Shell boots, how it discovers which App belongs at the current URL, how that App is loaded as a federated remote, and how the App's own router and framework runtime come up inside the shared page.

== Problem

A OneCX page is a micro-frontend host. The Shell owns the `window`, the `history` object and the top-level router, while each App is a separately-built bundle (Angular module or React/Vite build) that has to start up *inside* that host and stay synchronised with the same URL. Several things have to line up for the first pixel of an App to appear:

* the Shell must load, before anything else, the framework runtimes that the first App will need (the *pre-loaders*);
* the Shell must fetch the workspace config to learn which routes — and therefore which App — exist;
* the Shell must register and load the matched App as a Module Federation remote; and
* the App must boot its own framework and router *without* duplicating the shared runtime and *without* fighting the Shell for control of the URL.

Nothing of this is visible to the end user, but every startup delay or "blank page" is rooted here. This Area explains the mechanism end-to-end.

== Big picture

The libraries provide the building blocks; the Shell orchestrates them. The split looks like this:

[source]
----
  libs (onecx-portal-ui-libs)                     Shell (onecx-shell-ui)
  ------------------------------------------------
  @onecx/angular-webcomponents  ----->  bootstrapModule / WebcomponentConnector
  @onecx/react-webcomponents    ----->  createViteAppWebComponent / SyncedRouterProvider
  @onecx/angular-utils          ----->  toLoadRemoteEntryOptions (MF consumer)
  @onecx/build-utils            ----->  shared-dependency policy for every bundle
  @onecx/accelerator            ----->  getLocation() (shared base-path helper)
----

At startup the Shell is both a consumer and a provider of Module Federation: it loads every App/Remote Component as a remote, and it exposes its own toast Remote Component. The sequence, in short:

[source]
----
index.html
  -> main.ts (MF entrypoint): load pre-loaders, then import bootstrap
  -> bootstrap.ts: setCapabilities + bootstrapModule(AppModule, 'shell')
  -> app initializers: workspace config -> routes -> seed shared URL
  -> router.activate(matched route) -> loadRemote(App)
  -> App mounted in <router-outlet> (Angular NgModule) or as a custom element (web component)
----

Each step is explained once, in its owning Unit below.
