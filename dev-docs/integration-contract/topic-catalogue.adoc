This Unit covers Unit 8 of the link:README.adoc[Integration Contract & Topics] Area. It is the reference table for this Area: every shared `Topic` and `Gatherer` the libraries define, with its version, its publisher and consumers, and the Area that owns its meaning. Units 1–7 explain the contract these entries are built on; this Unit is the index of the concrete entries.

== Question answered

What shared `Topic`s and `Gatherer`s do the OneCX libraries define, and for each, what is its version, who publishes it, who consumes it, and which Area owns its meaning?

== Why it exists

The messaging contract (Units 1–6) is general; the concrete channels are the pieces every other Area builds on. A single list of all `Topic` and `Gatherer` implementations, pinned to the current `main` code, answers two questions a reader needs: *which* Topics exist (and at which version), and *where* the detail for each one lives (its owning Area). It also makes the contract auditable — a new Topic or a version bump shows up here as a row.

This Unit lists the entries but does not re-explain them. The *mechanism* of a Topic is Unit 1–4; the *meaning* of each Topic belongs to the Area that owns it; this page is the cross-reference table.

== How it works

A `Topic` is a `name`/`version` pair that subclasses the framework-agnostic base `Topic` (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]) and, for request/response, carries `sendGetMessage = false`. A `Gatherer` is a `name`/`version` pair that subclasses the base `Gatherer` (link:{libs}/accelerator/src/lib/utils/gatherer.ts[`gatherer.ts`]). Every concrete entry in `@onecx/integration-interface` is a thin subclass that only fixes the name, version and (for RPC Topics) the flag; the tables below were taken from those subclass definitions on `main`.

Two columns need a definition before the tables:

* *Publisher* — the unit that normally publishes the Topic's value. For shared state that is the Shell; for Topics an app publishes at bootstrap it is the App/Remote Component; for RPC Topics the *ask* and the *answer* differ, so both are named.
* *Consumers* — the framework adapters that wrap the Topic so app code can read (and, where relevant, write) it. See link:framework-adapters.adoc[Framework adapters].
* *Owning Area* — the Dev Docs Area that explains the Topic's *meaning*. Links point at the planned slugs in the link:{dev-docs-index}[index]; they are listed in the PR where the target page is not written yet.

== Libs side / Shell side

=== Libs side

`@onecx/integration-interface` defines every entry in the tables: the `Topic` subclasses under `src/lib/topics/`, the `Gatherer` subclasses under `src/lib/gatherers/`, and all exported from the package barrel (link:{libs}/integration-interface/src/index.ts[`index.ts`]). Two entries live outside the shared package: `TranslationCacheTopic` in `@onecx/angular-utils` and the guards `GuardGatherer` in `@onecx/angular-utils/guards` and `@onecx/react-utils`.

=== Shell side

The Shell is the *publisher* for most shared-state Topics and the *answerer* for the `PermissionsRpcTopic` it owns (link:{shell}/src/app/shell/services/permission-proxy.service.ts[`permission-proxy.service.ts`], parameters publishing in link:{shell}/src/app/shell/services/parameters.service.ts[`parameters.service.ts`]). The Shell advertises which of these Topics it provides through the capability list covered in link:versioning-and-capabilities.adoc[Unit 6].

== Angular / React

The catalogue itself is framework-agnostic, but the *consumers* column differs per framework: the Angular adapter is an `@Injectable` service and the React adapter a context/hook, wrapping the same `Topic` (link:framework-adapters.adoc[Unit 7]). The framework-agnostic services (`IconService`, `NotificationService`, `ImageRepositoryService`, `DynamicTranslationService`) are shared across both.

== Edge cases & pitfalls

* *The table is a snapshot of `main`.* `Topics` are versioned per directory; a new `v2/` folder is a new row, and a version bump changes the `Version` column. If this page and the code disagree, the code wins.
* *`name` and class name can differ.* `CurrentWorkspaceTopic` publishes under the name `currentPortal`, and `RemoteComponentsTopic` under `remoteComponentsInfo`. The transport channel is keyed on `name`|`version`, not the class name (link:transports-and-tab-scope.adoc[Unit 3]).
* *`sendGetMessage = false` is not "RPC only."* `IconTopic`, `EventsTopic` and `ResizedEventsTopic` suppress the initial `TopicGet` for other reasons (Unit 2); only some of them are true request/response channels.
* *Two classes per resized Topic.* `ResizedEventsTopic` (the read side) and `ResizedEventsPublisher` (the publish side) are separate classes that share the name/version; they are one catalogue entry.

== Debugging

To watch a concrete Topic or Gatherer from the catalogue, enable its namespace with `localStorage.debug` and reload — `localStorage.debug = '@onecx/accelerator:Topic:<name>'` for a Topic (look up the concrete `name` in the linked Topic definition, e.g. `CurrentWorkspaceTopic` declares `currentPortal`) and `localStorage.debug = '@onecx/accelerator:Gatherer:<name>'` for a Gatherer (e.g. `GuardGatherer`). Add `:error` to a `*` pattern to see only errors. General cross-App tracing is in the planned Unit link:../diagnostics/tracing-communication.adoc[Tracing cross-App communication] (Area 13).

== Known issues

* *`TranslationCacheTopic` runs ahead of the rest at version 2.* Every other Topic in this catalogue is at version `1`; `TranslationCacheTopic` is the live example of a bumped version (link:versioning-and-capabilities.adoc[Unit 6]).
