This Unit covers Unit 7 of the link:README.adoc[Integration Contract & Topics] Area. Units 1–6 explain the messaging contract (why it is message-based, how a message is delivered, where it travels, its lifecycle, request/response, and versioning). This Unit explains *how that contract is exposed to app code*: how Angular services, React contexts and the ngrx store connectors wrap the framework-agnostic `Topic` so that application code never touches a raw `Topic` instance.

== Question answered

How do the Angular, React and ngrx adapters wrap the framework-agnostic `Topic`, who owns and destroys each `Topic` instance in each framework, and how does a Topic value reach the ngrx store?

== Why it exists

Units 1–6 establish that the contract between the units on the page is the framework-agnostic `Topic` in the `@onecx/accelerator` (link:why-message-based.adoc[Unit 1], link:message-delivery.adoc[Unit 2]). But application code should not have to manage that primitive directly: a `Topic` is a *subscription*, not a value — it owns a `window` listener and one or two `BroadcastChannel` handles for its whole lifetime (link:topic-lifecycle.adoc[Unit 4]). Handing raw `Topic`s to app components would leak those resources and would force every app to handle the `isInitialized`/replay contract itself.

The adapters solve this with two rules:

* *One `Topic` instance per adapter instance.* An Angular service creates one `Topic` per service instance, and each React provider/hook call resolves its own `Topic` instance unless a parent passes one in. Distinct instances still communicate over the same shared `name`/`version` channel.
* *The adapter owns the lifecycle it stores.* The adapter is the place that keeps a `Topic` reference and calls `destroy` at the framework lifecycle point its implementation uses. App code only sees an observable, a service, a React context value or an ngrx action.

The same contract is served by three layers: the framework wrappers (Angular services, React contexts) and the ngrx store connectors that push a Topic value into the app's store.

== How it works

The adapter sits *above* the `Topic` and never changes its behaviour: it only (1) creates or accepts a `Topic` reference for that adapter instance, (2) exposes its current value to the framework, and (3) destroys it at the right lifecycle point.

* *Creation is lazy per adapter instance.* An Angular service holds the `Topic` behind a getter that creates it on first access (`this._config$ ??= new ConfigurationTopic()`), so that service instance keeps one `Topic` reference and can hand that same instance to other consumers (link:{libs}/angular-integration-interface/src/lib/services/configuration.service.ts[`configuration.service.ts`]). React's `AppStateProvider` calls `useTopic` separately for each state topic, and `useTopic` creates a new instance whenever no external topic is passed (link:{libs}/react-integration-interface/src/lib/contexts/appStateContext.tsx[`appStateContext.tsx`], link:{libs}/react-integration-interface/src/lib/utils/use-topic.utils.ts[`use-topic.utils.ts`]).
* *The value is exposed through `asObservable()` / `isInitialized`.* Angular reads a value with `firstValueFrom(topic.asObservable())` and surfaces the `topic.isInitialized` promise; React subscribes the topic into React state and surfaces `isInitialized` in the context value (Unit: Angular / React below).
* *The `Topic` may be injected.* Every Angular service getter is paired with a setter that accepts an externally provided `Topic` (`set config$(source)`); the React `useTopic(valueTopic, TopicClass)` hook likewise uses an external instance when one is passed. This is how a parent (for example a Remote Component host) shares a single `Topic` across several child wrappers instead of each creating its own.
* *Destroy is delegated to the accelerator.* The adapter only calls `topic.destroy()`; what `destroy` releases — and the one listener it leaves behind — is covered by link:topic-lifecycle.adoc[Unit 4].

== Libs side / Shell side

=== Libs side

The framework wrappers live in the framework-specific packages, each built on the same `@onecx/integration-interface` `Topic` classes:

* `@onecx/angular-integration-interface` — `@Injectable` services (link:{libs}/angular-integration-interface/src/index.ts[`index.ts`]).
* `@onecx/react-integration-interface` — React contexts and the `useTopic` hook (link:{libs}/react-integration-interface/src/lib/utils/use-topic.utils.ts[`use-topic.utils.ts`]).
* `@onecx/ngrx-integration-interface` — ngrx store connectors (link:{libs}/ngrx-integration-interface/src/lib/store-connector/store-connectors/index.ts[`store-connectors/index.ts`]).

A few adapters are *framework-agnostic* and live in `@onecx/integration-interface` itself so both frameworks can share them: `IconService`, `NotificationService`, `ImageRepositoryService` and `DynamicTranslationService` (link:{libs}/integration-interface/src/lib/services/icon.service.ts[`icon.service.ts`]). The Angular and React layers are thin: for example the Angular `IconService` imports the shared one from `@onecx/integration-interface` (link:{libs}/angular-integration-interface/src/lib/services/icon.service.ts[`icon.service.ts`]).

=== Shell side

The Shell is the publisher of shared state that app adapters consume, and it also uses Angular adapter services itself. In link:{shell}/src/app/app.module.ts[`src/app/app.module.ts`] the Shell initializes Angular `ConfigurationService` via `configurationServiceInitializer`, and publishes workspace and location state through `AppStateService` (`publishCurrentWorkspace`, `urlChangeListenerInitializer`). In link:{shell}/src/app/shell/services/routes.service.ts[`src/app/shell/services/routes.service.ts`] it publishes loading and current-MFE updates through Angular `AppStateService.globalLoading$` / `currentMfe$`, and reports remote-load failures through Angular `PortalMessageService.error`. Because the Shell is the tab's host, the Topics it publishes stay alive for the tab's lifetime rather than being destroyed per route (link:topic-lifecycle.adoc[Unit 4]).

== Angular / React

Only the wrapper and the destroy point differ; the underlying `Topic` is identical.

* *Angular.* Each shared mechanism is wrapped in an `@Injectable` service that owns one `Topic` and destroys it in `ngOnDestroy`. `ConfigurationService` holds a lazily-created `ConfigurationTopic`, publishes the loaded config on `init()`, exposes `isInitialized` as `topic.isInitialized`, and calls `config$.destroy()` on teardown (link:{libs}/angular-integration-interface/src/lib/services/configuration.service.ts[`configuration.service.ts`]). `AppStateService` aggregates several state `Topic`s (workspace, current page/MFE/location, global loading/error, authentication) behind one service and destroys each in `ngOnDestroy` (link:{libs}/angular-integration-interface/src/lib/services/app-state.service.ts[`app-state.service.ts`]).
* *React.* The `useTopic(valueTopic, TopicClass)` hook creates a `Topic` lazily (only when no external instance is passed) and destroys the instance it created on unmount. Unmount destruction is deferred by a zero-delay `setTimeout`, guarded by a mounted ref, so a StrictMode double-mount does not destroy a `Topic` the component immediately reuses (link:{libs}/react-integration-interface/src/lib/utils/use-topic.utils.ts[`use-topic.utils.ts`]). A context then subscribes the topic into React state and exposes `isInitialized` (link:{libs}/react-integration-interface/src/lib/contexts/configurationContext.tsx[`configurationContext.tsx`]).
* *Cleanup is the one structural difference.* Angular destroys every stored topic reference in `ngOnDestroy`, including one assigned through a setter, so a shared external topic can be torn down when the service goes away (link:{libs}/angular-integration-interface/src/lib/services/configuration.service.ts[`configuration.service.ts`], link:{libs}/angular-integration-interface/src/lib/services/app-state.service.ts[`app-state.service.ts`]). React destroys only the `Topic` it *created*; a `Topic` supplied as an external instance is left for its owner to destroy (link:topic-lifecycle.adoc[Unit 4]).

=== ngrx store connectors

For ngrx apps, the Angular side does not stop at a service: a store connector subscribes the (shared) `Topic` and dispatches a store action, wiring the Shell context and the URL to the app's ngrx store. Each connector is provided by a `provideXStoreConnector()` helper that registers the connector as an environment initializer (link:{libs}/ngrx-integration-interface/src/lib/store-connector/store-connectors/current-workspace-store-connector-service.ts[`current-workspace-store-connector-service.ts`]). For example `CurrentWorkspaceStoreConnectorService` injects `AppStateService`, subscribes `currentWorkspace$` until the service is destroyed, and dispatches `OneCxActions.currentWorkspaceChanged` (link:{libs}/ngrx-integration-interface/src/lib/store-connector/store-connectors/current-workspace-store-connector-service.ts[`current-workspace-store-connector-service.ts`]). The connectors bridge to the owning Areas via the planned `state-management/` slugs (link:../state-management/shell-context-to-store.adoc[Shell context → App ngrx store]).

== Edge cases & pitfalls

* *The adapter is the only place that should create a `Topic` for app code.* Bypassing the adapter and constructing a `Topic` in a component defeats the adapter-instance and lifecycle rules and leaks the `Topic`'s resources (link:topic-lifecycle.adoc[Unit 4]).
* *Sharing one `Topic` across wrappers.* Because each Angular service getter has a setter and `useTopic` accepts an external instance, a parent can hand one `Topic` to several wrappers so they observe the same channel instance. React preserves external ownership in that setup, but Angular service teardown still calls `destroy()` on the stored reference, so setter-injected topics are *not* safely caller-owned once assigned.
* *Angular services vs Shell lifetime.* An Angular `OnDestroy` fires per route/component, while the Shell's Topics live for the tab. Passing a Shell-owned topic into an Angular adapter risks destroying the Shell's shared instance when that adapter is torn down; React's external-instance path does not have that teardown side effect.
* *Publishing is delegated.* Publishing a Topic from the adapter (for example `ConfigurationService.init()` publishing the loaded config) is ordinary `Topic` publishing — the await/resolve semantics are Unit 2's, not the adapter's.

== Debugging

Each `Topic` and `TopicPublisher` logs under the `@onecx/accelerator:Topic:<name>` and `:TopicPublisher:<name>` namespaces (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]); a `Gatherer` under `@onecx/accelerator:Gatherer:<name>` (link:{libs}/accelerator/src/lib/utils/gatherer.ts[`gatherer.ts`]). Enable them with `localStorage.debug` and reload:

* `localStorage.debug = '@onecx/accelerator:Topic:*'` — every topic's traffic and drop/accept decisions.
* `localStorage.debug = '@onecx/accelerator:Topic:<name>'` — one concrete topic.
* `localStorage.debug = '@onecx/accelerator:Topic:*:error'` — only errors for all topics.

Watch `isInitialized` to confirm the adapter received the value its `TopicGet` requested (the Shell published it), and confirm wrappers only share a `Topic` instance when that same external instance was passed to them. General cross-App tracing is in the planned Unit link:../diagnostics/tracing-communication.adoc[Tracing cross-App communication] (Area 13).

== Known issues

* *The `window` listener survives `destroy`.* The `Topic` the adapters destroy is subject to the capture-flag mismatch described in link:topic-lifecycle.adoc[Topic lifecycle]: a destroyed `Topic` can keep a live `window` `message` listener. The adapters do not change this — they call the same `destroy()` the `Topic` defines.
